# D-23 design note — per-repair funding starves entries that pay a torch install on every re-execution

> **Tag words, added by the Phase D update.** This note predates the relabel of D-36: where it says MEASURED it means API-REPORTED (a stored field of a committed record; a dollar figure is the sandbox API's reported operation cost, not account billing). Numbers without a tag in this note are quoted from sources or are planning arithmetic, not results.

Status: **open**. Design only; no code. Nothing here has been run, and no number below is a result of the proposal.
Every number carries a tag: MEASURED (a stored record field), DERIVED (parsed from a quoted record line), ESTIMATED (a cost-guard
estimate, or a planning estimate made in this note). Ledger: $10.1349 [ESTIMATED: $9.8507 MEASURED + $0.2842 ESTIMATED], lower bound (D-27).

## The problem, as the records show it

Two entry-runs of the harness-v1.3.4 gate ended `INDETERMINATE` / `COST_CAP` while a runner install step was still running, before the
repository's own command started.

**Entry 8** — record `harness-v1.3.4/treatment/08@cf7e86f9580bb99147920b33d6481c61f55506e979bb75ee354527a6e2610bf9`
- entry cap $0.7819 [MEASURED, `cost.per_entry_cap`]: the entry inherited what was left of the gate cap;
- operation-1 (baseline) spent $0.3172 [DERIVED], leaving $0.4646 [DERIVED] — `[cost_guard] recorded $0.3172 sandbox spend, $0.4646 remaining today` (`events[8].line`);
- operation-2 (the time machine's re-execution) was funded for 55 s [DERIVED] and stopped at 55 s [DERIVED] —
  `[time-machine] stopped: daily cost ceiling reached: a sandbox operation reached its budget-derived limit of 55s` (`events[23].line`);
- the step that was killed had run 33 s [DERIVED] and was the torch install — `killed after 33s: pip install torch torchvision torchaudio --index-url https://download.pytorch.or` (`cost_guard.cost_events[0].note`);
- the killed step's spend is an estimate: $0.2842 [ESTIMATED, `cost_guard.estimated_sandbox_spent_usd`].

**Entry 11** — record `harness-v1.3.4/treatment/11@697388c90f63cf594426e76a616763dc1718637b9f66b9bb1d95c6438de2a21a`
- entry cap $2.0 [MEASURED]; four sandbox operations spent $0.3201, $0.3454, $0.3119 and $0.2889 [each DERIVED, `events[8]`, `[18]`, `[31]`, `[44]`];
- the wall clock each operation was started with shrank as the budget was used: 600 s, 198 s, 156 s, 119 s [each DERIVED] —
  `[sandbox] starting build+execute (wall_clock_seconds=119)` (`events[42].line`, and `events[6]`, `[16]`, `[29]` for the others);
- operation-4 (repair 2, a gate-approved patch) stopped at 119 s [DERIVED] with $0.72 [DERIVED] of the entry cap unspent —
  `[repair 2] stopped: daily cost ceiling reached: a sandbox operation reached its budget-derived limit of 119s` (`events[45].line`);
  its passport outcome is `gate_passed_not_executed`.

The mechanism: every re-execution rebuilds the environment from the base image, including the runner's torch install, and each
operation is funded from what is left of the entry cap. A later operation is therefore funded for less time than the install alone
needs, and the patch it was meant to test never runs. The cap works as a cap; it fails as a schedule.

## Two mechanisms, compared

| | A. Cached torch layer | B. Per-operation floor |
|---|---|---|
| What it does | Build the runner environment (Python minor, torch family pins, NumPy cap) once per entry as an image, and start every re-execution from that image | Before starting an operation, compare the seconds it can be funded for with the seconds the install is known to need plus the smoke limit; if it cannot finish, do not start it |
| Removes the cause | Yes: the install is paid once, not per operation | No: the install is still paid per operation; fewer operations fit in the cap |
| What it saves | Install seconds on every re-execution after the first | The spend of an operation that was going to be killed (entry 8's killed step: $0.2842 [ESTIMATED]) |
| New sandbox path | Yes: image creation and reuse touch `sandbox.py` / `runner_env.py`, so the seal rule requires a full live seal verification | No sandbox code changes if it lives in the cost guard and orchestrator only |
| Reproducibility | A cached layer is state between runs. METHODOLOGY declined snapshot images for harness-v1.3.2 for that reason; the cache key (base image digest, Python minor, every pin) and the layer's image id would have to be stored in the record and shown in the passport | None |
| Evidence it needs | The install's duration as a stored field. Today it is not stored: the only figures are DERIVED from event text | The same field, to set the floor from records instead of from a guess |
| Failure it can introduce | A stale or wrong layer silently changes the environment under test | A floor set too high stops repairs that would have fitted |

Reading: B is a guard, A is the fix. B alone turns "killed mid-install" into "not started", which is cheaper and honest but recovers
nothing. A is what would let a third operation of an entry reach the repository's command. Both need the same prerequisite: the
harness must store `funded_seconds`, `wall_seconds` and per-step durations as record fields (they are DERIVED today).

## What a validating gate would have to measure

Pre-registered before any run, on the same two entries (8 and 11), TREATMENT only:
1. no operation is stopped during a runner install step (stored field, per operation);
2. every gate-approved change reaches a re-execution: no attempt with outcome `gate_passed_not_executed` caused by the cap;
3. install seconds per operation, stored as a field, for the first and for each later operation (A must show the later ones near zero);
4. no entry over its cap, and the killed-step estimate (if any) flagged as before;
5. for A only: the layer's cache key and image id are in the record, and a second build of the same key gives the same environment (lock comparison).

The verdicts are reported but are not the criterion: D-23 is validated by operations reaching the repository's command, not by a recovery.

## Estimated cost of that gate

All ESTIMATED, built from MEASURED past spend; none of it is authorised (the stop rule stands).
- seal verification, required for A only: the harness-v1.3.4 seal cost $1.3125 [MEASURED]; a repeat would cost about $1.3 [ESTIMATED];
- the two entries: their harness-v1.3.4 spend was $1.2825 [MEASURED] and $0.6781 [ESTIMATED: $0.3939 MEASURED + $0.2842 ESTIMATED]; with both run to
  the entry cap of $2.0 [MEASURED] the upper bound is $4.0 [ESTIMATED];
- total: B about $2.0 to $4.0 [ESTIMATED]; A about $3.3 to $5.3 [ESTIMATED].

## Annotations, 2026-10-01 (v1.4.0 directive and the Step 0 budget note `docs/design/v1.4.0-budget.md`)

Added beside the note above; nothing in it is edited.
- **Reclassified from design limit to defect.** The owner's v1.4.0 directive names the per-operation rebuild as the root cause of the two
  `COST_CAP` endings above (entries 8 and 11). The records support exactly that: two of the four v1.3.4 gate losses were install-bound;
  #03 ended on the silent exit (D-25) and #07 installed no torch (budget note, finding 1). The directive's "three of the four" is not used.
- **"~90 s torch install" is withdrawn.** The figure appeared in the v1.4.0 directive, is in no record, and is not used anywhere in
  RERUN's documents. What the records give: whole baseline operations of 80-85 s [DERIVED] and one install step killed after 33 s [DERIVED].
- **The CPU wheel index is already in use** for every recorded torch install; nothing to change there except storing the install seconds.
- **Images already persist within one operation** (`sandbox._run_once` keeps every non-final step's image until its `finally`). The defect is
  that none survives to the next operation. Mechanism A of this note ("cached torch layer") is what harness-v1.4.0-rc implements, as
  per-step layers reopened by UUID; its reproducibility condition (the layer's identity and image id in the record) is met by the new
  per-operation record fields `branch_from_image`, `result_image`, `image_kept`, `install_seconds`, `sandbox_seconds`.
