The mechanism: the harness asks the model to guess where the program exits and to print there. One guess costs one repair attempt and one
sandbox operation. The exit site is a fact the interpreter knows; the harness should record it instead of asking for a guess.
`PYTHONFAULTHANDLER` (added for D-19) does not help: a deliberate exit is not a crash.

## Proposed mechanism

The harness already runs the documented command through its smoke launcher with extra environment variables and never edits the
command. The same route can carry diagnostics.

1. **Exit-site hook (primary).** The launcher puts a harness-owned directory on `PYTHONPATH` holding a `sitecustomize` module. It
   - wraps `sys.exit`, `builtins.exit`, `builtins.quit` and `os._exit` so that the call records `traceback.format_stack()` and the exit code before the original runs;
   - registers an `atexit` function that prints the recorded stack, the exit code and a fixed marker line to stderr.
   An `atexit` function alone is not enough: by the time it runs, the frames that called `exit` are gone. That is why the stack is captured
   at the call and only printed at exit. `os._exit` skips `atexit`, so its wrapper prints immediately.
2. **Trace fallback.** A bare `raise SystemExit(1)`, an exit from a C extension, or an exit in a child process is not seen by the wrappers.
   If the first run is silent and the marker line is absent, one further re-execution runs the same command as
   `python -X dev -m trace --trace <script>` and keeps only the tail of the output: the last lines executed before the exit.
   `-X dev` also turns on the interpreter's own warnings and fault handler. Tracing slows the program a great deal, so this run may reach
   the smoke limit before the exit; the record must say which of the two happened.
3. **What the repairer receives.** The exit stack (file, line, function) as evidence. The D-19 gate rule stays: without an exit site, a
   code patch may still only add diagnostics.
4. **Recording.** The attempt stores the exit site, how it was obtained (`exit_hook` or `trace`) and the marker, as fields, so a passport
   shows them as MEASURED. The harness files are outside the repository tree, so the tree-integrity check is unaffected; that must be tested.

Limits, stated now: the hook changes the process under test (wrapped functions, an extra `sitecustomize`); a repository that ships its own
`sitecustomize` or replaces `sys.exit` needs a rule; a silent exit caused by a signal or by the sandbox is a different failure and stays
with the existing classes.

## What a validating gate would have to measure

Pre-registered before any run, on entry 3, TREATMENT only:
1. the record of the first silent re-execution contains an exit site (file and line) obtained by `exit_hook` or `trace`, as stored fields;
2. the exit site is inside the repository tree and the quoted line is an exit call or a `raise SystemExit` (checked against the pinned commit);
3. the next repair proposal names that file, and no attempt is spent on a diagnostics-only patch;
4. on a control command that exits normally, the hook adds no output and the exit code is unchanged (seal-verification case, both smoke outcomes);
5. the trace fallback, when used, records whether the exit or the smoke limit came first.

The verdict is reported but is not the criterion: D-25 is validated by the exit site being in the record, not by a recovery. Knowing where a
program exits does not make the exit repairable; the reason may be missing data or a missing GPU.
