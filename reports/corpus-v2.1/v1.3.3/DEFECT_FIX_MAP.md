## Execution budget (step 1.7)

Repair re-executions (time machine, build-isolation step, every repair) run the documented command under `smoke_exec` for 60 s: a command that
finishes keeps its own exit code and output; one still running at 60 s with output and no traceback passes (`RERUN_SMOKE_ALIVE`) and is stopped;
a silent one, or one that printed a traceback while running, fails. The as-published baseline run is not wrapped. Every such attempt records
`execution = {"mode": "smoke", "seconds", "outcome"}` and the passport hashes it. A pass therefore means "ran for 60 s without failing", not "completed"
and not "reproduced"; RESULTS for v1.3.3 will say so wherever RUNS_AFTER_REPAIR appears.

## What changes CONTROL behaviour (so CONTROL v1.3.2 may not stay the baseline)

- the cost rule does NOT touch the baseline run (revised before any run): it keeps the 600 s wall clock, so CONTROL is unchanged by it. (The first design shortened the baseline to ~176 s; the v1.3.2 records showed 3 of 20 CONTROL operations at 195-494 s with normal cost, so it was dropped.);
- the classifier's denoising can change the evidence/taxonomy text of a CONTROL record whose output carried warnings or progress bars (cannot be proven from the stored records, which keep only the chain evidence);
- the runner's NumPy cap changes the environment of a repository that itself declares torch < 2.3 (candidates: entries 5, 9, 17). It does not change entries whose torch is undeclared, because the cap follows a torch PIN, and in CONTROL an undeclared torch is installed unpinned.
Everything else in v1.3.3 is behind `repair_enabled` (time machine, repair, Tavily, patch pipeline, smoke) and cannot touch CONTROL.
